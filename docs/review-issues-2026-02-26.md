## 问题 1：严格优先策略与实现不一致
- 现象：
  - 当“地区优先/已拥有优先”设置为“严格优先”时，排序结果仍会先按覆盖数决定。
  - 用户感知为“严格优先没有生效”。
- 根因：
  - 排序函数在 strict 逻辑前就执行了覆盖数早返回（`coverageDiff`）。
- 风险：
  - 配置语义与实际行为不一致，影响推荐可信度。
- 解决计划：
  - 调整排序顺序：当任一策略为 strict 时，先比较 strict 维度，再回落到覆盖/效率。
  - 非 strict 模式继续沿用覆盖优先。
- 验证点：
  - 构造覆盖数不同但 strict 维度差异明显的方案，确认 strict 维度优先。
  - sameCoverage / sameEfficiency 行为不回归。

## 问题 2：空态误判（过滤导致 0 与真实无方案混淆）
- 现象：
  - 推荐结果为空时统一提示“当前组合无可用方案”，但其中一部分实际是“被隐藏开关筛掉了”。
  - 用户无法区分“无解”与“筛选导致看不到”。
- 根因：
  - 页面使用 `!recommendations.length` 直接分支，没有结果原因分类。
- 风险：
  - 错误引导用户去拆分刷取，而不是调整筛选开关。
- 解决计划：
  - 在推荐模块新增空结果原因：`filteredOut` / `noScheme`。
  - 模板分支改为：
    - `filteredOut`：提示“当前筛选已隐藏全部结果，请调整筛选开关。”
    - `noScheme`：提示“当前组合无可用方案”（仅异常场景）。
  - 对“待刷=0且仍有推荐”的场景增加信息提示，不阻断推荐展示。
- 验证点：
  - 场景 A：筛选开关导致目标被完全隐藏，应显示 `filteredOut` 提示。
  - 场景 B：待刷为 0 但有推荐，仍展示推荐并显示“无需刷取”信息提示。
  - 场景 C：真实无方案（异常数据场景）显示 `noScheme` 提示。

## 问题 3：备注输入框高度只增不减
- 现象：
  - 文本域输入长文本后再删除，输入框高度不回落。
- 根因：
  - 自适应算法将当前高度当作基准，导致高度被抬高后无法收缩。
- 风险：
  - 移动端列表可视区域被持续挤占。
- 解决计划：
  - 重写高度计算流程：先 `auto`，再按 `minHeight~maxHeight` 夹取，允许回缩。
  - 保持超出上限时滚动条行为不变。
- 验证点：
  - 连续输入/删除后高度可双向变化。
  - 空内容时回到最小高度。
